# Deployment

Index DTF deployment is a transaction-building workflow.

The SDK prepares deployment calls and approval plans. Apps own wallet UX, transaction submission, log parsing, and route navigation after deployment.

## Deployment Types

| Type                    | Builder                                                |
| ----------------------- | ------------------------------------------------------ |
| Ungoverned DTF          | `prepareDeploy` or `prepareDeployPlan`                 |
| Governed DTF            | `prepareDeployGoverned` or `prepareDeployGovernedPlan` |
| Vote-lock staking token | `prepareDeployStakingToken`                            |

The DTF deploy builders take `version` (`"5.0.0"` | `"6.0.0"`) and deploy through that version's per-chain deployer;
Folio 6.0 deploys also take the v6 details. See the [SDK deployment page](/sdk/deployment#folio-60-deployment).

## Initial Basket

The deployment basket uses raw token amounts.

```ts
basicDetails: {
  name: 'Example Index DTF',
  symbol: 'eDTF',
  assets: [tokenA, tokenB],
  amounts: [1000000000000000000n, 2000000000000000000n],
  initialShares: 1000000000000000000n,
}
```

## Flags

The SDK exports default deploy flags.

```ts
import { DEFAULT_INDEX_DTF_DEPLOY_FLAGS } from "@reserve-protocol/sdk";
```

Defaults:

- trusted filler enabled
- weight control enabled
- price control set to `1`
- bids enabled

## Logs

After sending the deployment transaction, parse logs with the same target the deploy builder took:

```ts
const address = extractIndexDtfDeployedAddress(receipt.logs, { chainId, version, deployer });
const stToken = extractIndexDtfDeployedStakingTokenAddress(receipt.logs, { chainId });
```

Only events emitted by the expected deployer count (`getIndexDtfDeployerAddress(target)`, or the chain's governance
deployer for staking tokens): a basket token can emit a lookalike `FolioDeployed` during `transferFrom`. A receipt
without the deployer's event throws `RECORD_NOT_FOUND`; one where the deployer names more than one address throws
`INVALID_RESPONSE`. Do this after confirmation, not before.
